# 2027 Life OS — Project Guidelines

These rules are binding for every change to this project.

## Behavioural model

The app is a habit system, not a to-do list. Two rules carry it and neither is negotiable:

- **Three tasks a day, hard capped.** `TOP_TASK_CAP = 3` is enforced in state, not hidden in the UI — a fourth pick is refused and told why. Loosening the cap defeats the 80/20 principle the whole screen exists to serve. The cap has **four doors** now and `capToday()` holds every one of them: the matrix's promote, the day rollover (`applyPrep`), a hand-edited or imported payload (`migrate`, repaired once at schema 24), and the evening prep (`prepShape` slices its picks, `prepPickAdd` refuses the fourth outright). A guard that lives only on the button it was written for is a guard that four new call sites will walk around — the screen's job is to *say why*, never to be the only thing saying no.
- **Five habits carry the score, not eighteen.** `CORE_CAP = 5`, and `disciplineOf()` reads `scoredOf()` — the core when one is set, every habit when none is. This is the same 80/20 the task cap serves, arrived at the hard way: eighteen habits meant three real wins on a Sunday rendered as **17%**, a screen telling someone who did three hard things that he failed. Every consumer of the score goes through `disciplineOf`/`scoredOf` — the ring, the archive row, the streak and the reminder the server sends — or they will divide by different denominators and disagree about the same day. The fallback to all habits is a floor, not the resting state: while no core is set the routine screen shows the invitation, because a feature that waits to be found in settings never is. **`migrate()` must never guess the core** — which five habits carry someone's day is not a question a migration is in any position to answer, so schema 20 sets `core: false` for everyone and asks.

- **«اليوم» is the screen the app opens on, and it owns nothing.** It aggregates: the next prayer, the three tasks (the same `TopThree` the routine renders, never a copy), the habits still open, today's lectures off the university desk, and the nearest exam or deadline — read from `uni.tasks` and the calendar's own rows together. Every number on it is derived; a figure stored a second time here would be a second day disagreeing with the first. It is deliberately short, because a landing screen that lists everything is the sixteen-tab sidebar with extra steps. **A fresh open lands on it; a reload comes back where he was** — `sessionStorage` tells the two apart, and it has to, because the conflict bar's «حمّل الأحدث» and a follower window both reload and must not be answered with a landing page.
- **A card has one home, and «اليوم» is where the day's state is read.** The three tasks, the prayer times and the water meter were rendered on the routine *and* on «اليوم», which is the duplication the landing screen exists to end: two screens showing the same number is two screens to check, and the routine is for *managing* habits rather than reading the day. So `TopThree`, `PrayerCard` and `WaterCard` are rendered once, on «اليوم». The last two moved whole into `life-today.jsx` and are exported like every other block there — they take `place` / `count` / `goal` as props and keep nothing, so putting either back on the routine is one import and one line. `clampGoal` still bounds the cups wherever the meter is rendered.
- **The day's blocks have one order and one current block.** `BLOCK_IDS` in `life-state.mjs` is canonical — `GROUPS` in `LifeOS.jsx` fastens the label, icon and tint onto it the way `NAV_META` does for the tabs — and `blockAt()` in `prayer-times.mjs` answers which one is open from the prayers, never from clock hours. Before the first block opens, the answer is the *last* one: 00:30 is «قبل النوم» of an evening still going on, the same reason `inReflectWindow()` runs past midnight. A test holds `BLOCK_IDS` against `BLOCK_ANCHORS`, because a day cannot run in two orders.
- **A habit is ticked in one place.** `useHabitTick` holds the tick, the reading prompt and the withdrawal on an untick; the routine screen and «اليوم» both call it. Two copies of that arithmetic is the day the shelf keeps pages he undid.
- **A day nobody recorded is written down as one.** `{ date, gap: true }` — no `pct`, no `done`, no `all` — because an empty square in the month grid cannot otherwise say whether the day went to zero, was never opened, or has not happened yet, and an average taken over "the rows that exist" flatters every stretch where the recording stopped. `fillGaps()` writes them, `migrate()` filled the old holes once and `rollDay()` writes the days a closed laptop missed; `isGap()` is the one test for one. Gaps are **counted out loud and never averaged** — «يومان بدون تسجيل هذا الشهر» is the fact that explains the number above it. Every consumer that must not see them already gates on `Array.isArray(row.done)`, which is why a gap row carries neither a score nor a roll call. Reach is bounded by `GAP_REACH` (120 days, the same depth the server keeps daily snapshots to): past four months a dashed square is not information, and an unbounded walk from a stale `date` is years of empty rows pushing real days out of an archive capped at `HISTORY_CAP`.
- **Yesterday stays open for as long as today lasts.** «عدّل أمس» rewrites one archive row through `setDayDone()` and moves nothing else — today's habits do not shift, because today is a different day and the whole value of a hard boundary is that it holds. It works on a gap row too, which is the common case: the day he did not open the app is exactly the day worth going back for. **A past day's score goes through `pctOfRow()`, which goes through `disciplineOf()`** like everything else — and it scores the roster the row actually recorded, deleted habits included. Dropping them was tried and is wrong twice over: it rescores a finished day every time the routine is edited (re-opening yesterday showed 21% beside the 35% it was lived at), and it makes the denominator disagree with the roll call, which lists a missing habit as «عادة لم تعد في روتينك» rather than forgetting it. After an edit the streak is **recomputed from the rows** by `streakBaseFrom()`, never nudged — a counter adjusted by hand is a second opinion about the same archive.
- **Tomorrow's three are chosen tonight, and they own nothing.** A day's three tasks get picked the night before or they get picked at ten in the morning by whatever shouted loudest, so `TomorrowModal` asks for them inside the evening window — the same `inReflectWindow()` the reflection uses, because it is the same hour and the same question. It is read from «اليوم» as a card that only ever *reads*, and from a button of its own on the routine screen that is always open: the evening is the right default and the wrong only door, since a prep already written has to be re-readable at any hour. **The prep stores no task text and no time.** A pick is `{ task, event }` — a task id out of the same `state.tasks` the matrix edits, and the id of the calendar entry its hour created. The first step is written onto the task row as `task.step` and `TopThree` shows it under the task, on both screens, because a task is a sentence and the step is the thing a body can start. An hour belongs on the calendar; a copy of it on the prep would be a second appointment disagreeing with the first, so setting a time creates a real `eventShape` row, changing it moves that row, and clearing it deletes it. **`prep.for` is what makes the prep safe to carry**: `applyPrep` promotes it only on the day it names and `prepCarry` clears it the moment that day arrives — prep on Monday night, open on Thursday, and Monday's three are not promoted onto a day they were never chosen for. Picking for a different day than the one in hand starts over rather than appending, for the same reason. With nothing prepared the rollover leaves his flags exactly where they were, which is the behaviour this app had before the screen existed and the behaviour it keeps for every day the screen is never opened.
- **The streak forgives one day and never two.** `streakRunFrom()` walks back from yesterday and steps over `STREAK_FORGIVE = 1` consecutive misses; the one after that ends the run. A day under `STREAK_TARGET`, a gap row and a missing row are all the same thing to it — a miss — because a day he was away is exactly what the tolerance is for. **Forgiven is not counted.** `days` only ever counts days that actually cleared the bar, so no softening can inflate the number; the tolerance comes back as `forgiven` and the toast **says it out loud**, for the same reason a gap is counted and never averaged — a tolerance nobody can see is a number quietly meaning less than it used to. A miss still pending when the walk ends is not forgiven: forgiveness is only granted by a day that followed it and kept going, or a run of three would report a tolerance it never used. **The counter is gone.** `rollDay` no longer does «+1 if yesterday banked, else 0» — that arithmetic cannot forgive anything, because it does not know what the day before yesterday was. It reads `streakBaseFrom(history)` off the rows it has just filled, which is what `setDayDone` has done after every correction since the rule existed, so there is one answer and not two. The copy changed with the rule: a run with a forgiven day in it is not «متتالٍ», so every site says `countedWord(n)` («يوم مُحتسَب» / «يومان مُحتسَبان» / «أيام مُحتسَبة»), counted through `arCount` like every other live number.
- **Every habit may carry the smallest version of itself.** `habit.min` is one line the user writes — «عشر دقائق مشي» under «ساعة في النادي» — and `habitShape()` is the one place a habit's fields are written, like `taskShape` and `bookShape`. It exists because the day a run dies is never the day something was hard, it is the day something was impossible and the only move left was to skip it and watch the number fall. **A tiny tick is a tick**: it counts for the score, the streak and the archive, it goes through `useHabitTick` like every other tick (`toggle(id, true)` — a second argument, never a second hook, or the reading withdrawal and the undo become two implementations drifting apart), and it fires the same `los-pop`/`los-ripple`/`los-reward`, because a completion that pays out less than the one beside it reads as worth less and the whole point of the floor is that taking it is not a defeat. It is only *marked* differently: `tiny` rides on the habit beside `done` and resets with it at the rollover, and the archive row carries `tiny: [ids]` as a **subset of `done`, never a third state** — merged onto the row like everything else written per-day. **`migrate()` never writes a floor**, the same refusal as the core five: which smaller version he would accept on a bad day is a question only he can answer.
- **Two days away gets a door, not a verdict.** `comebackFrom()` counts the unrecorded days immediately before today — `gap` rows and missing rows, never days that scored zero, which is the distinction gap rows exist to make — and at `COMEBACK_MIN = 2` «اليوم» opens on `ComebackCard` instead of on the ring. Somebody opening this app after a week away is opening it for a verdict, and the verdict a broken streak and a 0% ring deliver is «you failed, and here is the number»: that is the moment the app gets closed for a month, and no amount of accurate arithmetic makes it a useful first sentence. So the card shows the smallest surface there is — `scoredOf()`'s habits that are still open, and the same `TopThree` — the streak chip is hidden while it is up, and the days away are stated once, flatly, with no number attached to blame. It owns nothing: same flat array, same `useHabitTick`, same `TopThree`. It **closes and stays closed for the rest of the day**, kept in the UI preferences beside the reflection's snooze, because a card that says «نبدأ بأقل شي» and reappears after every tick is the nagging it exists to replace. The walk is floored at the first day he ever recorded — greeting a new profile with «رجعت» is nonsense.
- **A delete keeps what it replaced for eight seconds.** `UndoBus` carries `arm(label, before)` to every destructive button in the tree — a context rather than sixteen props, because a new delete that forgets to take the callback is a new delete with no undo. **The bus lives in `life-shared.jsx`, never in `LifeOS.jsx`**, because the imports only run one way: a context declared in the entry point is a context every carved-out module is cut off from, and a delete that moves into one of them loses its undo on the way out with nothing failing to say so. `FinanceModule`'s two deletes spent a day like that — the buttons kept working and the eight seconds had quietly stopped existing. The provider and the toast stay in `LifeOS.jsx`, where the state and the fixed bar are; only the wire is shared. `before` is the **whole array**, not the row: a habit put back at the end of the list is a habit in the wrong block and the wrong order, which is its own small loss. It is spread over whatever the state is by then, so an unrelated change made in those eight seconds is not undone with it. **It may also be a function of that state**, for the one shape a plain slice cannot express: a row that lives *inside* an object rather than in a top-level array. A reminder sits in `state.bot` beside the water window and the two brief times, so `{ bot: wholeBotObject }` would quietly revert a toggle flipped a second after the delete — `(s) => ({ bot: { ...s.bot, customs: kept } })` puts back only what was deleted. Unticking a habit is armed too — it withdraws the evening's reading sessions and rolls the page counter back, which is a deletion in everything but name.
- **A pomodoro is a rhythm, not a countdown.** The focus desk's state is a *phase* — `run.phase` is «جولة تركيز», «راحة قصيرة» or «راحة طويلة» — because the hour that actually gets lost is the one spent "just finishing this" through a break that never came, and a timer that only counts down is the half of the technique that cannot protect it. So a rhythm is one row carrying its round **and both of its breaks** (`presetShape`: `min`/`brk`/`long`/`every`): a ninety-minute cycle followed by five minutes is not a rhythm, and one global break length guarantees that one of the two presets is wrong. The break arms *and* starts itself by default; the next round does not, because a round nobody chose to begin is a round nobody committed to.
- **The run is state, and a run found already over is settled by one function.** `state.focus.run` is persisted and counted off an absolute `endAt`, so a reload mid-round comes back on the right second — and a reload is not rare here: the conflict bar's «حمّل الأحدث» reloads, a follower window reloads itself. `settleRun()` draws the only line that matters: a round whose bell rang within `RUN_STALE_MS` (6h) is written down, a round **still counting** when it went stale writes nothing (nobody can say when he left it, and minutes nobody can vouch for are worse than no minutes because every number above them becomes a guess), and a round he **paused** keeps its minutes exactly — a pause is the one moment the amount worked is known. A stopped round is logged too, as the minutes it actually was and marked `full: false`; the old timer wrote nothing unless the round finished, so eighty minutes of a ninety-minute round simply never existed. **A break never writes a row**: `state.sessions` has meant «جلسة تركيز» since the day it existed — in the data-health panel, in the recovery centre's counts and in every total on the screen — and filing rest in it would make all three say something they do not mean. `migrate()` never turns `autoDone` on, the same refusal as the core five and the habit floor: twenty-five minutes is not evidence that a task is finished, so the end-of-round sheet asks instead of a timer ticking a task he then has to go and untick.
- **Six pillars hold the year.** Every 2027 goal belongs to one of `PILLARS` (الإيماني، الصحي، المهني، المالي، الاجتماعي، الشخصي). A goal with no pillar has nowhere to live.
- **Ninety days at a time.** Every goal also carries a `quarter`, and the vault opens on `currentQuarter()` — the other three are one tap away but never the default. A year-wide list is what the quarters exist to prevent.
- **The cue advances on every open, and on tap.** `useDailyQuote()` walks `QUOTES` from a cursor persisted at `life-os-2027:quote` and returns `[quote, shuffle]`; the card is a button. Keying it to the day of the month was tried and rejected — within a single day the card never visibly moved, which reads as broken. A cue only motivates when it is actually new.

**A habit can feed the library.** `habit.book` is the link and has exactly three states: `null` (an ordinary habit), `READ_ACTIVE` (follows whichever book is marked «أقرأه الآن»), or a book id (pinned, for a second reading habit). Ticking a linked habit opens `ReadLogModal` **after** the tick has landed, never before — the reward animation must play and a skipped prompt must still leave the habit done. Logging appends to `state.reading` and advances that book's `page`. **Unticking withdraws it**: today's sessions for that habit are removed and the page counter rolls back, because a log that keeps pages the user undid is worse than no log. The seeded «قراءة» habit ships linked to the active book, and `migrate()` links an existing one the same way — a feature that needs a settings hunt before it does anything will never be found.

**A page logged is half the transaction; the point it left is the other half.** The shelf counted pages from the first day it existed and kept nothing about what they *gave* — so «قرأت ٢٠ صفحة» was a number, and the sentence he could still say about those pages a week later lived nowhere. `habit.book` fed the counter; nothing fed the reader. So the bot asks one question after every logged reading — «وما أكبر فائدة من قراءة اليوم؟» — and `addNote` writes the answer onto the book with the page it was read at. It **asks and never waits**: nothing is pending, no answer is expected, and ignoring it costs the point and nothing else, which is the same refusal of pending state the evening reflection makes. It asks **once an evening** — a book that already carries a point written today has had this conversation, and a prompt that arrives after the thing was done is the prompt that teaches you to stop reading them.

**A point that never comes back is a quote, not a lesson.** `noteShape` is the one place a point's fields are written — the book desk and the bot both go through it — and it carries `box` (how many times it came back and was remembered) and `due` (the day it comes back next), walked up `REVIEW_STEPS` (1, 3, 7, 21, 60 days). The reminder sends **one point and never a digest**: five fragments in one bubble is a wall nobody recalls anything from, which is the opposite of the exercise. It sends the **cue first** — the opening four words — and the point itself behind one tap, because re-reading a note is not recall and only recall keeps anything; a point short enough to have no cue is shown whole rather than quizzed on nothing. Remembered widens the gap, forgotten returns it to tomorrow at the bottom of the ladder, and **never to an empty `due`** — an empty one means «waiting», and a forgotten point must not read the same as one nobody has ever seen. **`migrate()` writes no schedule**: an older point has no `due`, an empty `due` is read as due now, and that is both the honest reading of a point nobody has reviewed and the whole migration — the same arrangement a reminder's `repeat` arrived under. Like every other periodic reminder it is **off by default and silent when nothing is due**, and the one button under a point he remembered is «اجعلها مهمة», because a benefit that never becomes an action is a beautiful quotation.

**Which book is a question, and a wrong answer is the one number nobody re-checks.** «قرأت ١٠ صفحات من سيكولوجية المال» names its book, so `findBooks` matches the shelf — folded like `findHabits`, then word-overlap in both directions, then a bigram `nearness` that only breaks a tie when it is decisively closer (`NEAR_MARGIN`). «سكليوجية المال» is the ordinary case rather than the awkward one and must land; «المال» fits two titles equally and must **ask**. A title that is not on the shelf is not a dead end — it is the first sentence this feature will ever meet — so one tap adds the book, marks it «أقرأه الآن» and logs the pages as **one write with one undo**, because an undo that took the pages back and left a book nobody chose would be half an undo. And pages landing on a book **move it to the head of the shelf**: «أقرأه الآن» is not exclusive, every reader of it takes the first match (`activeBook`), and the next sentence is usually «فائدة …» with no book named in it.

**The evening prompt belongs to the logical day, not to the wall clock.** `inReflectWindow()` is true from `REFLECT_FROM_HOUR` (20:00) round past midnight to `DAY_START_HOUR` — because that is when this day actually ends. Testing `getHours() >= 20` left 00:00–03:59 silent, which is exactly when someone reviewing the day that just finished is awake, and exactly the hours «السهر بعد منتصف الليل» assumes he is up for; at 04:00 the day rolled over and took the question with it. «لاحقًا» snoozes for an hour and the prompt returns at most `REFLECT_MAX_SHOWS` times an evening — a button that says *later* has to mean later, and one that returns forever is one you learn to dismiss without reading. The snooze lives in the UI preferences, so a reload does not re-pop it. It also has a button of its own on the routine screen: the automatic prompt only fires inside its window on a day that fell short, and the reflection must be reachable, re-readable and editable outside both conditions.

**The reading goal is the second discipline meter.** `state.readGoal` (default `READ_GOAL_DEFAULT`) drives the tracker bar, and `readStreak()` counts days in a row that met it. A streak whose last qualifying day was yesterday still counts today — the day is not over, and zeroing it at midnight would punish someone who reads in the evening.

**Every book has a desk.** A shelf that only holds titles and a star rating is a list, not a library. `bookShape()` is the single place a book's fields are written — seed, add form and migration all go through it, so they cannot drift. `BookDesk` is where the reading actually lives: the summary, the points (each with the page it came from, reorderable), where the reading has reached, and the one takeaway. The card stays scannable and shows only a progress bar and a note count; the desk is the place you come back to. Finishing a book stamps `finishedAt` once and moving it back out clears the stamp, so the shelf never claims a finish that was undone. `READING_QUOTES` seeds `state.reads`, a second cue list about reading, walked by the same `useDailyQuote` under its own `READ_KEY` — the hook takes a key precisely so a second cue does not fight the first one's cursor. The cue itself is `ReadingCue` in `life-shared.jsx` and it renders on «اليوم», not here: a cue that only appears on the screen he visits once a week is a cue he never reads. It takes a list and owns nothing, so putting it back on the shelf — or onto the routine — is one line.

**The user owns the order, the cues and the image.** Habits reorder by drag and by ↑/↓ arrows — the arrows are not redundant, they are the only path that works under a finger, because HTML5 drag never fires on touch. Reordering splices `state.habits`, the one flat array the blocks are a filtered view of; a per-block list would drift out of sync with what the archive and the discipline count read. `QUOTES` is seed only: it is copied into `state.quotes` on first load, after which the user adds, edits and deletes freely, and the cue card falls back to an invitation rather than a blank when the list empties. `state.cueImage` is a data URL redrawn through a canvas and stepped down until it fits `IMAGE_BUDGET` — the whole app shares one storage quota, so an oversized photo would make every later write throw and silently stop persisting *everything*. The image gives way; the habits and history never do.

The daily routine runs in six prayer-anchored blocks — الصباح، بعد الظهر، بعد العصر، بعد المغرب، بعد العشاء، قبل النوم — and every habit in every block feeds the one discipline score. The blocks follow the prayer times, not clock hours; a generic "المساء" is not a slot this user lives by.

## UI / UX

- **The ground is the sky, and it moves with the day.** `SKY` holds six phases — `night`, `fajr`, `sunrise`, `day`, `asr`, `maghrib` — selected by `skyAt()` from the wall clock and re-checked once a minute by `useSkyPhase()`, so a boundary that arrives while the app is open changes the screen instead of waiting for a reload. `SkyBackdrop` paints it: a vertical gradient, a sun or a masked crescent moon inside a wide faint halo, drifting cloud, and a seeded star field. Morning is sunrise and cloud and daylight; night is stars and stillness. This is the third ground the project has had and the two before it were both rejected as gloomy — first a blue-slate dashboard (`#0F172A`), then warm charcoal (`#2A2028 → #1B1418 → #120C10`, later deepened and lit harder). Neither failed on hue. They failed because a single fixed dark colour behind a discipline tracker reads as a monitoring console at every hour of the day. **Do not replace the sky with a static ground.**
- **A card's fill comes from the phase, not from a constant.** Each `SKY` entry carries `veil` and `veilStrong`; the root sets them as `--los-veil` / `--los-veil-strong`, and `GLASS.backgroundColor`, `T.card` and the sidebar all read the variables. Cards stay dark so white type keeps its contrast, and they *must* darken as the sky brightens — a fixed `rgba(255,255,255,0.0x)` fill turns into a pale smear against a noon horizon, which is exactly how the Eisenhower quadrants shipped broken once. **Any surface that sits directly on the sky uses `T.card`, never its own white alpha.** The veils are also tinted toward their own phase so a card belongs to the scene instead of sitting on it as a black slab.
- **The veil runs in two directions, and which one is not a taste call.** A card has to be *visible against the sky behind it*, and the sky changes sides: at `night` and `fajr` the ground is near-black, so the veil is a **lift** (a tinted white alpha — cool moonlit blue at night, warm rose at fajr) and a dark fill would make the card vanish into the ground; from `sunrise` through `maghrib` the ground is bright, so the veil is a **deepening** and a white alpha becomes the pale smear described above. Deepening every phase for a more "premium" look is therefore a way to delete the cards at night, and it is the first thing to check when someone asks for a darker theme.
- **Depth is shadow, not fill.** The 3D of this UI comes from `GLASS.boxShadow` carrying a whole elevation ramp at once — an inset top highlight and an inset bottom shade to give the pane thickness, then a tight contact shadow, a mid shadow for the lift, and a wide faint ambient one. A single wide shadow reads as fog under the card; one hard shadow reads as a sticker. This is also the *cheap* place to buy depth: shadows are painted, while a wider `backdrop-filter` re-samples and re-blurs the sky on every frame the card moves, which is the bill `GLASS`'s 12px blur and `content-visibility` both exist to keep down. **So when a card needs to feel deeper, reach for the shadow stack and never for the blur radius.** `.los-raise` is the hover form of the same idea — lift plus a deeper stack, on the app's own `cubic-bezier(.22,1,.36,1)`, carrying no `will-change` (a compositor layer per card is exactly the scroll cost being avoided) and reduced to a shadow-only change under `prefers-reduced-motion`. **Hover belongs in CSS**: the book card used to set `boxShadow` and `borderColor` from `onMouseEnter`/`onMouseLeave`, and because the leave handler wrote `boxShadow: "none"` it stripped the card's glass elevation permanently the first time a pointer crossed it.
- **Override a Card's fill with `backgroundColor`, never `background`.** The shorthand wipes `GLASS.backgroundImage` and the card loses its sheen along with its fill — this is what happened to the quadrants.
- **Nothing opaque may sit above the sky.** `SkyBackdrop` is `fixed inset-0 -z-10`; the root carries no background of its own, and the phase colour goes on `document.documentElement` so an overscroll bounce matches. Giving the root a solid `backgroundColor` paints straight over the sky — this already happened once.
- **The sun is a halo, not a disc.** A single hard-edged circle reads as a billiard ball. The light spreads wide and faint and only a small blurred core is bright. The moon's bite is cut with an SVG mask, never painted as a second disc in a flat colour — the gradient behind it is never exactly that colour at the moon's height, so the flat disc read as an eclipse.
- **Screen headings carry a coral→gold gradient** via `.los-title`. The clip is paired with `-webkit-text-fill-color: transparent`, and nothing on that element is ever animated with a transform — see the rendering trap below.
- **Every colour is saturated.** Semantic: Coral `#FF5722` action, Emerald `#10B981` success, Amber `#FFB020` achievement, Rose `#FF3B5C` danger. Organizational tints are vivid too — `#FFB020`, `#FF7A45`, `#FF4D8D`, `#9D5CFF`, `#00C2FF`, `#5B8CFF`. Muted pastels were tried once and rejected: they read as washed-out and drained the life the app exists to create. Do not re-introduce them.
- **A category tint must never colour a completion.** If a row's "done" state borrows its category colour, finishing something stops reading as finishing. Pass `T.primary` to `Checkbox`, and let the category colour its own icon and progress bar only.
- **Glassmorphism on every card:** the sheen is *warm*, not neutral white — a trace of coral at the lit corner falling through transparency to violet at the shaded one, so a card picks up the ground's colour instead of sitting on it as a grey pane. `border: 1px solid rgba(255,225,210,0.18)`, `backdrop-filter: blur(12px) saturate(150%)`, and an inset top highlight at ~0.14 alpha. Frosted, not glossy. **12px and not 22px, and that is a correctness rule rather than a taste one.** A glass card re-samples the sky behind it and re-blurs it on every frame it moves, so the cost of a scroll is the number of blurred cards on screen times the radius of each — not the length of the page. Behind a veil this dark the two radii are hard to tell apart, so the cheaper one is the honest default, and anything wider than `GLASS` needs a reason. The same bill is why `Card` carries `los-surface` and the stylesheet gives it `content-visibility: auto`: a card scrolled out of view is then not laid out, styled, painted or blurred at all. `.los-cue` is excluded deliberately — the property implies paint containment and that card's two glows sit outside its own border box — and `contain-intrinsic-size: auto 220px` is what keeps the scrollbar still. `SkyBackdrop` takes a compositor layer of its own (`translateZ(0)` plus `contain`) so seventy stars and four gradients are rasterised once instead of on every scrolled frame.
- **Interactive motion eases out, never in-and-out.** `cubic-bezier(.22, 1, .36, 1)` is applied by attribute selectors on Tailwind's own `transition*` classes, from a `<style>` block that ships after Tailwind — same specificity, later in the document, so it wins without `!important`.
- **Electric Coral `#FF5722` drives every primary CTA** — add a habit, add a task, add a book, save, the active nav item. One CTA colour, used everywhere, so the next action is never ambiguous.
- **Emerald `#10B981` means success only** — a completed habit, a finished task, a day above target. Never decorative, and never a group tint.
- **Amber `#FBBF24` means achievement** — star ratings, streak counters, the morning block.
- **Every completion pays out.** Checking a habit or a task fires `los-pop` (scale-bounce), `los-ripple` (expanding ring) and `los-reward` (emerald glow pulse on the card). A completion that animates nothing is a bug.
- **Navigation is split by breakpoint, never duplicated.** Desktop (`lg:flex`) gets the collapsible sidebar; mobile (`lg:hidden`) gets `BottomTabs` — a floating glass bar clear of the bottom edge via `env(safe-area-inset-bottom)`, with short labels from `NAV[].short`. Anything fixed to the bottom on mobile (the streak toast) must clear the bar.
- **A row that leaves its list on the tick is held until the reward has played.** On «اليوم» the list is what is *still open*, so ticking removes the row — and the ripple, the pop and the glow all fire on something already unmounted, which is a completion that pays out nothing. `remainingIn(habits, block, keep)` takes the ids to keep listed and `REWARD_HOLD` (1100ms, longer than the 700ms burst) is how long they are held. On a timer, never `requestAnimationFrame`.
- **«اليوم» is the first tab and stays out front.** `migrate()` places it at the head of `navOrder` rather than letting `orderNavIds` append it, because a sixteenth tab opens behind «المزيد» on a phone — which is the opposite of a screen whose job is to be the one the app opens on. Same hand-placement as «مسار التوظيف» in schema 14 and the two tabs in schema 17, and the same guard: a tab he has already positioned keeps where he put it.
- **Four tabs on the bar, the rest behind «المزيد».** `TAB_BAR = 4` — in `life-state.mjs`, because it is also a floor on the state and not only a width: at 375px a tab needs ~63px to keep its label legible, so the bar shows the first `TAB_BAR` tabs plus a More button that opens a sheet with the remaining tabs and Settings. Adding a tab means adding it to the sheet, never widening the bar.
- **Which tabs take a row is his, like the order is.** `navSplit(navOrder, navMore)` cuts one order in two — the tabs the navigation shows, and the tabs that answer only from «المزيد» — and both the sidebar and the phone bar read it. `navMore` starts at `MORE_IDS` (the knowledge map, which is read occasionally and never on the way through a day) and is edited from the same place the order is, by the ☰ on each row. **A pushed-back tab keeps its place in `navOrder`**: that is why they are two lists and not one, because a tab pulled back out has to return where he put it rather than to the end. The floor lives in `navSplit`, not in the editor — tabs are released from the top of his order until `TAB_BAR` are out front, so no saved payload can leave a phone with an empty bar; the editor only *says why* the button is disabled. The sidebar has a «المزيد» disclosure of its own, lit when the tab inside it is the one on screen.
- **A tab's name, its order and the component it opens are three questions with three answers, and none of them is a `switch`.** `NAV_IDS` says which tabs exist, `NAV_META` fastens the label and the icon, `navOrder`/`navMore` are the user's, and **`SCREENS` in `LifeOS.jsx` maps each id to the component it opens** — one table, read by one line (`SCREENS[tab]?.(screenCtx)`). The chain of `{tab === "x" && <X …/>}` it replaced was sixty lines in which the answer to "what does this tab open?" was spread across the render, so adding a screen meant editing JSX in the middle of the shell and threading its props past everything above it. Every entry is a **function returning JSX**, deliberately: a page is then a composition rather than a component, and putting the matrix underneath the routine is editing one line in one table instead of moving code between files. The props arrive as one `screenCtx` built in a single place, so a new screen takes what it needs and ignores the rest instead of adding its fifth prop to the shell's signature. Adding a tab is three registrations — `NAV_IDS`, `NAV_META`, `SCREENS` — and a test already holds the first against `SIDEBAR_GROUPS`.
- **A screen is a list of blocks, and reordering it is moving a line.** «اليوم» is the worked example: its render is seven named components one under the other, each exported, each stateless, none of them aware of what sits above or below it. The alternative — the four-hundred-line inline JSX tree it replaced, where a card was a `<Card>` buried three levels inside a grid — meant that "put the cue above the tasks" was a careful cut-and-paste with a real chance of unbalancing the tree. Blocks are also why the same card can appear on two screens without either importing the other. **A block takes everything it draws as props and keeps nothing**, which is what makes moving it safe; the moment one reaches back into the screen's own state it stops being a block and the next person to move its line gets a `ReferenceError`.
- **Date and time sit beside the wordmark**, small — `NowStamp`, its own component so the one-second tick re-renders that line and nothing else. It is named `NowStamp` and not `Clock` because `Clock` is already a lucide icon in this file.
- Smooth transitions on every interactive state. Respect `prefers-reduced-motion` — every `los-*` animation is disabled under it (including `los-drift`, the cloud motion), and `usePrefersReducedMotion` gates both the SMIL gradient on the discipline ring and the star twinkle.

Five rendering traps this UI has already hit:

- **Never put a `transform` animation on the same element as `-webkit-background-clip: text`.** Chrome collapses the clip and the text paints as a solid block. Animate a wrapper instead, and always pair the clip with `-webkit-text-fill-color: transparent`.
- **Never drive a reward animation through `requestAnimationFrame`.** It does not run in a hidden tab, so the reward is swallowed and then replays when the tab returns. Set the state synchronously and clear it on a timer.
- **`Modal` renders through a portal into `document.body`, and must keep doing so.** A transformed ancestor becomes the containing block for every `position: fixed` descendant, and `.los-in` — the wrapper that slides each screen in — animates `transform`. Every modal is rendered from inside a module, so without the portal each one is laid out against the module's content box instead of the window: the tallest form put its own header above the top edge, where nothing can scroll to it. Capping the height treats the symptom; leaving the transformed subtree is the fix.
- **Never set a CSS shorthand beside one of its own longhands in the same `style` object.** React applies them in object order and a re-render can have the shorthand wipe the longhand. This has bitten twice: `background` erasing `GLASS.backgroundImage` (the quadrants lost their sheen), and `textDecoration` beside `textDecorationColor` on the checkbox label. Use the longhands — `backgroundColor`, `textDecorationLine`.
- **A button inside a `draggable` element does not get clicked.** Chrome reads the press on the button as the start of a drag the moment the pointer moves a pixel; the drag is cancelled because nothing was dropped, and no `click` ever fires — so the control works for a perfectly still hand and does nothing for any other, which is indistinguishable from a dead button. The nav order editor shipped that way once. `draggable` is armed by the grip handle alone (`draggable={grip === n.id}`, set on the grip's `mousedown`, cleared on `dragend`, `mouseup` and `mouseleave`), never on the row. Any new row that carries both a drag and a button follows it.
- **Never centre a `.los-in` element with `-translate-x-1/2`.** The animation owns `transform` on that element, so Tailwind's translate utility is simply discarded and the bar hangs off the right edge of the screen — the same collision as the clip trap above, one property down. Centre a fixed bar with `sm:inset-x-0 sm:mx-auto sm:w-[…]` instead, which needs no transform at all. All four top/bottom bars (save failure, conflict, stray copy, disk stopped) use that form.

## Tech stack

- **React** (function components + hooks), **Tailwind CSS**, **Shadcn UI**.
- **Shadcn caveat:** shadcn is not an importable package — it is components you copy into a project with its CLI, compiling to Radix UI + Tailwind. This project ships as a single self-contained file, so `LifeOS.jsx` implements shadcn's *token model and component API* (`Card`, `Btn`, `Field`, `Badge`, `Modal`, `Checkbox`) with zero dependencies beyond `lucide-react`. Keep that contract: new primitives follow the same shape. If the project ever moves to a real build with its own `components/ui` directory, swap these for genuine shadcn components — the call sites should not need to change.
- Icons: `lucide-react`. No other icon set.

## Data

- **Always persist to `localStorage`**: habits, tasks, books, goals, sessions, income, ventures, prompts, reviews, pipeline, history, streaks, and UI preferences. A new feature's array goes in `freshState`, in the `carry` block of `loadState`, and behind a `migrate()` branch — miss the middle one and the data vanishes on the next day rollover.
- **A `history` entry is merged, never rebuilt.** The archive effect rewrites today's row on every discipline change, and that row also holds everything written about the day — the evening reflection (`distraction` / `fix`) and the accountability mirror (`mirror`). Spread the previous entry before writing, or a single habit toggle erases it. Anything new that is written per-day belongs on this row and inherits the same rule. **And the merge itself lives in `stampToday()`, not in the effect.** It was written inline in `LifeOS.jsx` while the app was the only writer of that row; the Telegram bot ticks a habit from a phone and has to write the same one, and two writers each with their own copy of this arithmetic is a bug waiting for the day they disagree. Everything on the row is derived from the state handed in — the score through `disciplineOf`, the roster, the day's holds and falls, the water — so the effect passes nothing and its dependency list only says *when* to re-stamp.
- **The money is two lists, and both have a shape.** `state.income` is what the hours paid and `state.expenses` is what the day cost; a single signed ledger would make «معدّل الساعة» read negative rows it has no business in. `incomeShape` and `expenseShape` in `life-state-finance.mjs` are the one place a money row's fields are written — added at schema 27, which is also the first time an income row was ever normalised: the screen had written its five fields inline, survivable only while the screen was the only writer. A bad amount becomes `0` and never `NaN`, because one NaN in a list makes every total on the screen unprintable. Both lists are bounded by `MONEY_CAP`: they are fed from a phone now, and a list with no ceiling is a payload that grows until a save throws.
- **The focus desk is state, and so is the round still running.** `state.focus` holds the rhythms (`presets`, bounded by `PRESET_CAP`), which one is picked, the daily goal, the six switches and `run` — the phase counting right now. It carries whole across a day rollover because a round begun at 03:50 is still being worked at 04:01; `focusCarry` resets `round` alone, since four rounds yesterday must not hand this morning's first round a long break. `state.sessions` is bounded by `SESSION_CAP` and every row goes through `sessionShape` — a row written before schema 29 carried a day and a length and nothing else, so the shape fills the rest with what an older row *means*: `planned` equal to the minutes worked, `full: true` (the old timer only wrote a row on completion) and no start hour, which is why the hour bands say how many rows they had to leave out rather than guessing.
- **What the bot sends unprompted is state, not configuration.** `state.bot` holds the two brief times, the three built-in reminders (water, the pre-prayer nudge, the task sweep) and up to `REMINDER_CAP` of his own — edited on «بوت تيليجرام» and saved like every other screen's work, because a schedule that can only be changed by editing a file on the machine the bot runs on is a schedule that never changes. **There is no command channel between the screen and the process**, and that is the point: the bot re-reads the disk once a minute and `Scheduler.sync` re-arms only when the plan it depends on has actually moved, so a schedule edited while the bot is switched off is still the schedule when it comes back. `planDay` is in the state layer precisely because *both* sides read it — the screen previews the evening the bot is about to arm, and a second reading would eventually disagree with it. **`migrate` never turns a reminder on**, the same refusal as the core five and the habit floor: what the bot may interrupt him for is not a question a migration can answer, so an older payload arrives with the two briefs on and everything periodic off — the coach and the weekly review included, and those two most of all, because one of them sends an opinion and the other is long. Every reminder's text is built from the day **at the moment it fires**, never at the moment it was armed — a water nudge armed at 07:00 that still says «باقي ٨ أكواب» at three in the afternoon has stopped being true — and `null` is a legitimate answer: a sweep with nothing to sweep is silent, because the message that fires to say «nothing» is the one that teaches you to ignore the rest.
- **A reminder that repeats only daily is a reminder for things you would have remembered anyway.** A weekday pattern already said «كل جمعة» — pick one day and the row is weekly — but nothing could say «يوم ٢٨ من كل شهر», which is the shape every recurring *obligation* has: the rent, the bill, the month's budget, the quarter's goals. So a custom reminder carries a `repeat` (`day`, `week`, `month`) and `REMINDER_REPEATS` is its table, named apart from the calendar's `REPEATS` and with different ids on purpose — an event recurs from a date it already has, a standing reminder has no date at all and must be told which days it comes back on, and a shared `monthly` meaning the event's own day in one reader and `dom` in the other would be the worse kind of reuse. One field says which, so no reader guesses from whichever other field happens to be filled. **The 31st is never a month skipped**: `firesOn` lands a `dom` of 31 on the last day of a month too short for it (`monthDays`), because a month skipped is a bill unpaid and «آخر يوم في الشهر» is what somebody who typed 31 meant. `migrate` guesses nothing — the shape reads an older row by what it already says, days picked meaning `week` and no days meaning `day`, so it fires on exactly the evenings it fired on before. **And the row says its next firing out loud** (`nextFireOf`, walking the same `firesOn` the bot arms from, bounded by `NEXT_REACH`): «يوم ٣١» read in February says nothing about whether February was understood, and a monthly reminder whose next date cannot be seen is one that cannot be trusted.
- **A reminder may buy its own silence.** `null` has always been a legitimate answer here — the sweep with nothing to sweep says nothing, the coach on a good day says nothing — and a reminder in his own words was the one thing left that spoke regardless: «اقرأ قبل النوم» at half past ten on a night the pages were already read is exactly the message that teaches you to swipe the rest unread. So a row carries `only`, one of `GATES` (عادة باقية، مهمة باقية، الماء، القراءة، التركيز), and `gateOf()` answers it **from the day at the moment the timer fires**, never when the plan was armed. The gate is not a filter on the plan: `planDay` arms a conditional reminder unconditionally, the same way it arms the coach, because whether there is anything worth saying is a question about a day still hours away. `gateOf` returns the *facts* and never the sentence — `pass`, `left`, `goal` — and the Arabic is written where every other sentence the bot sends is written (`gateLine` in `reminders.js`); it also hands back **what it was looking at**, which is how a conditional nudge gets its buttons with no new wiring at all: `water`, `tasks` and `habits` are the fields `bot.js` already builds keyboards from. The screen says «صامت الآن — الشرط مُستوفى» on a row whose condition is already met, because a reminder silent for a good reason and a reminder that is broken look identical from the outside.
- **The list offers the ideas rather than hiding them.** `REMINDER_IDEAS` is seed only, added by one tap and never by a migration — what the bot may interrupt him for stays his answer. It exists because an empty list with a text box above it tells nobody that a reminder can be monthly, or that it can be the kind that stays quiet when the thing is already done; two of those eight are the only way either feature would ever be found. An idea already taken drops out of the row, and a test holds every one of them against `reminderShape`: an idea the shape would normalise into something else is an idea that lies about what the tap adds.
- **The bot answers a question, and never files one.** Everything the parser does not recognise becomes a task, which is the right default for a *thought* — an unrecognised sentence is exactly what the inbox is for. It is the wrong default for a question: «كم صرفت هذا الشهر؟» was landing in «مهم غير عاجل» as a to-do item, which is a wrong answer *and* a row he then has to go and delete. So `askedAbout()` reads a question first — a leading question word, or a trailing «؟», and nothing else, however many subject words a sentence happens to contain — `ask.js` turns the topic into a sentence, and nothing is written. The subject words are matched **anywhere** in the sentence, which is the opposite of the trigger rule and correct for the same reason: a question's leading word is the question word, and what it is about comes after it. The window («هذا الشهر», «آخر ١٠ أيام») is read apart from the subject, because folding them together would need a table entry per pair.
- **The coach decides for itself whether to speak, and usually does not.** `advise()` in `insight.js` reads the whole day and returns a ranked list of observations; on a day that is going fine it returns an empty list and the scheduled coach sends **nothing at all**. That silence is the feature and not a shortfall — a coach that files a report every noon is a notification you learn to swipe unread, and the one noon it has something real to say is the noon you swipe that too. It is the same rule the task sweep already keeps, applied to a message whose whole content is a judgement. Three things follow from it. **`comeback` silences the rest**: a man opening this after a week away does not need the other eight things that are also behind, he needs one door, so that check returns alone. **Every observation carries the action that answers it** — «انتباه، انتظامك ٤٠٪» is a grade, «باقي عادتان — اضغط إحداها» is a move — as `{label, data}` callback strings, never a keyboard, because `insight.js` must stay loadable without grammY. And **it never invents a number**: every figure comes out of `disciplineOf`, `streakRunFrom`, `focusDay`, `weakSpots`, `readStreak` and the rest, or the bot and the screens would disagree about the same day by notification. `/coach` asked by hand has a floor under it (`coachReply`), because a button pressed that replies with silence reads as a dead bot.
- **The floor is a button, not a field.** `habit.min` counted for the score and the streak from the day it existed, and the bot's `tiny:` callback was reachable from nothing — the feature lived only in the state layer. `openKeys` now renders «◔ الحد الأدنى» beside every habit that has one, and so does the coach's streak warning, because the whole value of a floor is being visible at the moment skipping looks reasonable: on a phone, at the end of a bad day, which is exactly where that keyboard is.
- **A round can be started, paused and stopped from the phone, and `closePhase` is why that is safe.** The run is persisted state counted off an absolute `endAt`, so a round begun in a message and a round begun on the desk are the same row and either side can end it. The cycle counter, the session row and the next phase armed are one decision and have to stay one: a round logged without advancing the counter is a long break that never arrives, and a counter advanced without logging is a break earned by work nobody recorded. That arithmetic was written inside the desk's own `endPhase` while the screen was the only thing that could end a round; it is `closePhase` in `life-state-focus.mjs` now, and both writers call it. The **bell is its own timer** (`Bell` in `reminders.js`) and deliberately not one of the scheduler's: `planDay` is a list of minutes past midnight and cannot express a deadline that only exists once a round was started, and the run moves on every pause while the day's plan does not move at all. It rings only while the master switch is on — a round started on the laptop already rings there — and it **settles the run before it announces it**, because a round that finished while the laptop was shut has to be written down by somebody and this is the only process awake.
- **The weekly review is the one message that is not about now.** A day is too short a window to see a slope in, and the evening brief cannot show one: it reports today against nothing. `weekReview()` reports the average over the days that recorded, **the gaps counted out loud and never averaged**, the streak read off the rows, the habit the week says is steadiest and the one it says is hardest — with that habit's own floor offered beside it — then the pages, the minutes, the money and next week's deadlines. One day a week, because a review that arrives daily is a daily report, which is what the evening brief already is.
- **A reminder you cannot defer is a reminder you mute.** «لاحقًا» sits under every unprompted message (`Snoozer` in `reminders.js`, `bot.snooze` minutes), and muting one reminder is how the whole schedule gets switched off — the app's reflection prompt learned this already. What is held is the **entry, never the rendered text**: a water nudge deferred at eleven must say what is left at noon, which is the rule every sentence the bot sends already keeps and the one place holding the message would have broken it. In memory, like the undo bus, for the same reason.
- **The routine runs on prayers, so its nudges do too.** `bot.blocks` fires `after` minutes into each of the six blocks and lists that block's habits that are still open — silent when none are. A fixed 17:00 for «بعد العصر» is wrong by forty minutes in March and an hour in June, so `planDay` takes the block times the way it takes the prayer times: computed by the caller off `blockTimes()`, because the state layer may not import the solar maths. **Both callers pass them** — the bot arms from `planToday` and the hub previews from the same `planDay`, and a preview that leaves an argument out is a preview that disagrees with the evening it is previewing. **And `planDay` takes the day itself, never its weekday alone** — `whenOf` reads the weekday, the date and the length of the month out of one argument, because a monthly reminder needs all three and three arguments each caller has to keep in step is three ways for the preview to disagree with the evening it is previewing. `bot.events` is the other half of an event's `warn`, which is in *days*: right for an exam, useless for a four o'clock appointment. An untimed entry is never armed — it has no hour to be early for.
- **Forgetting is the normal case.** «أمس صرفت ٣٥ غداء» is read by stripping the day word and parsing the rest *exactly as it would have been*, so the two forms go through one code path and cannot drift; the days ride back on the reading as `back` and `backKey` turns them into a square. Only the readings that can carry a date take one — a task has no date of its own, and a habit's day is the archive's business. The reach is bounded at `BACK_MAX` (3 days): past that he is guessing, and a guessed row in a ledger is worse than a missing one. The confirmation **says which day it landed on**, because a row filed on a past square is only findable if the message said where it went. A habit backdated goes through `tickOn` → `setDayDone` — the same function «عدّل أمس» uses — and the streak is recomputed from the rows afterwards, never nudged.
- **An untick is a deletion in everything but name**, so the bot has one and it goes through the state layer. `withdrawReading()` in `life-state-books.mjs` removes the day's sessions for that habit and rolls the book's page counter back; it was written inside `useHabitTick` while the routine was the only place a habit could be unticked, and two copies of it is a shelf that disagrees with itself about where a book has reached. `tiny` leaves with the tick — `tiny` without `done` is not a state this app has.
- **The agent is a brain, never a pair of hands.** `agent.js` is the one place in this project a language model decides anything, and it decides *which* action — never *how* one works. Every tool in its table is a one-line redirect to a function `actions.js` already exports and `tests/bot*.test.mjs` already holds, so nothing the model can do was ever unreachable from a button, and the caps are the caps: a fourth task for today is refused by `capToday` with the model watching, and the refusal goes back to it so it says why instead of claiming a success. It is **called by name** — «مساعد …» or `/ai …` — and never silently replaces `parse.js`, because the rules are instant, free, offline and tested, and because knowing when you are talking to a model is the user's to know. **A turn is two phases, and splitting them is correctness not tidiness**: `runAgent` thinks against a *working copy* (its tools really run, so the model sees real results rather than imagined ones) and `applyPlan` replays that same list synchronously on fresh state inside `withState`'s lock. `withState` calls its change function synchronously, so handing it an async turn would leave `out.next` undefined and never call `postSync` — the write would vanish with nothing failing to say so. And one turn gets **one** undo: `keepBefore` merges oldest-wins, so three writes come back to before the turn, not to the middle of it. The success shape carries `skipped`, never `refused` — `apply()` reads `refused` as «nothing happened», an empty array is truthy, and a fully successful turn once replied «⚠️ » while its write sat on the disk. It is **off without `ANTHROPIC_API_KEY` and says so**, the same contract as the voice note, and the brief that goes out with every question is the day's figures and titles — not the archive — which is the real price of the feature beside the tokens.
- **A voice note ends where `parse` begins.** The transcript is replayed through the ordinary text handler, so every trigger, every question and every confirmation works unchanged and there is no second grammar to keep in step. It is the one feature here with a dependency outside this machine, so the seam is generic — anything speaking the OpenAI transcription shape, including a local `whisper.cpp`, which keeps the audio on the laptop. With no `VOICE_API_URL` it is off and **says so**; a voice note that vanishes silently is worse than one that was refused. The text is echoed back before anything is written, because a transcriber that heard «ثلاثمئة» for «ثلاثين» has to be caught by eye and not by a ledger that is quietly wrong.
- **The weekly chart costs no dependency.** Rendering the report agent's SVG as a photo would need an SVG-to-PNG converter — a new installed dependency in a repo whose build borrows everything and installs nothing. Block characters are a bar chart that renders identically on every phone and survives being copied out as text. Scaled against a stated maximum and **floored, never rounded**: rounding draws a 79% day at six bars of seven, which reads as a day that cleared the target it missed, and a chart about discipline may understate but may not overstate. A gap gets its own mark — «no bar» and «scored zero» are different facts, which is the whole reason gap rows exist.
- **The one thing the control hub cannot read off the disk is whether the process is alive.** A bot that has died cannot write down that it has died, so `health.js` opens a loopback listener on `BOT_PORT` and the screen polls it — bound to 127.0.0.1, never 0.0.0.0, with the reading open to any local page and `POST /ping` fenced by the same two tests the sync server fences a write with. The token never leaves that process: the body carries a masked chat id and what is armed, and nothing that could be used to become the bot. The strip stops polling entirely while the tab is hidden.
- **The browser is not the only writer any more, and the bot goes through the front door.** `services/telegram-bot/` reads `GET /state` and writes `POST /sync` like any other client — never `graphify-out/data/lifeos.json` directly, which would bypass the revision guard, `.prev.json` and `backups/guard/` in one move. It sends **no `Origin` header**, which is the seam the server already keeps open for «curl and this machine's own tools»; adding one would get every write refused. It reads the revision off the disk on every change rather than remembering it, and one promise chain serialises its own writes so two messages a second apart cannot both claim `rev + 1`. It brings the payload up to today through `migrate` then `rollDay` — the app's own `loadState` minus `localStorage` — because a tick written onto a payload still holding yesterday's ticks is a tick on yesterday's roll call. And when a window *is* open while the bot writes, that window's next save is refused and the conflict bar appears: «حمّل الأحدث» adopts the disk copy with the bot's row in it. That is the designed answer, not a bug.
- **An imported file is untrusted.** `SettingsModal` refuses a payload that is not shaped like this app's state before touching anything, then runs it through `migrate()` — an older backup must come back upgraded, not broken.
- **A task has one shape, like a book and an event do.** `taskShape()` is the single place a task's fields are written — the seed, the matrix's add form, the evening prep's quick-add and the migration all go through it, so they cannot drift into writing two different kinds of task. It is also where `step` gets its bound (`STEP_MAX`), and the bound trims rather than clears: text the user typed is never silently deleted on the way through a shape that runs on every load.
- **Changing seed data is a migration, never an edit.** `SCHEMA` lives in `life-state.mjs` and is the version; `migrate()` runs on load and reshapes an older payload. Bump `SCHEMA` and add a branch — moving a habit between groups must *move* the user's own row, not append a second copy beside it. Verify against a pre-migration payload before shipping.
- **The browser holds the working copy; the disk holds the one that survives.** Every save also goes to `services/local-sync-server.js`, which writes `graphify-out/data/lifeos.json` atomically, keeps the write before it as `lifeos.prev.json`, stamps an hourly snapshot into `backups/auto/` (72 deep) and a daily one into `backups/daily/` (120 deep, keyed to the *logical* day so a 01:30 write files under the day before). `pullDisk()` reads it back — but **only when `localStorage` is empty**, and **before the first render**: mounting first and adopting after would paint a seeded empty day, and the save effect fires on that seed and writes emptiness over the recovery still in flight. A cleared profile, a new profile or an evicted bucket heals itself on the next open. **The recovery carries the revision with it.** `pullDisk` lifts `rev` out of the response and seeds the counter from it; start a recovered profile at zero and its very first save arrives behind every revision the file already holds, the server is right to refuse it, and the only thing the user ever sees is a conflict bar that will not go away. The recovery is the one path where the counter is adopted rather than incremented, and `tests/split.test.mjs` holds it.
- **Only one origin writes to disk, and it is named.** `served()` is true for `http://127.0.0.1:47615` alone — not `localhost`, not another port, not `file://`. Each of those is a separate origin with its own `localStorage`, its own idea of the day and its own window lease, so two of them writing to one file is two copies of a year taking turns overwriting each other. A copy anywhere else still reads and still recovers; it shows «هذي ليست النسخة الأساسية» and never syncs. The server enforces the same rule from its side: `POST /sync` is refused unless the `Origin` is the one that server itself serves (no `Origin` at all is allowed, for curl and this machine's own tools). The one seam is `window.LIFE_OS_PRIMARY`, which a server started on any port but 47615 injects into the page it serves, so a throwaway test copy is self-consistent rather than a special case. Nothing in the live build sets it.
- **Every write carries a revision, and a write that is behind is refused.** The counter lives in its own key, `life-os-2027:rev` — never in React state, because it moves on every save and a re-render to announce a save is a re-render for nothing. The window remembers the revision it loaded; before each write it re-reads the stored one, and a stored revision ahead of its own stops the write dead and raises the conflict bar. The server applies the same test to the file on disk (`rev`, then `date`) and answers `409` with `{ rev, date }`; a successful write answers `200` with `{ rev, savedAt }`, which is the only thing the «القرص ✓» half of the save stamp is ever allowed to believe. The two ways out of a conflict are «حمّل الأحدث» (adopt the disk copy and reload) and «اعتمد هذه النافذة» (`X-Force: 1`, after which the server stows the file it is about to overwrite in `backups/guard/`). A payload with no `rev` is accepted — the counter has to start somewhere. **A write level with the file is refused too, unless it is the same payload.** The counter is per-window `localStorage`, so a window holding a stale snapshot keeps numbering its own saves and eventually hands up the number already on disk — at which point `mine < theirs` is false and last-writer-wins is back. That is how a 17-habit copy landed on top of a 22-habit one that had just been recovered from `backups/guard/`. So the server compares the contents at equal revisions, by a sha256 of the payload with its keys sorted: the same hash is one write sent twice and is answered `200` **without touching the file**, because rewriting it would push the real previous generation out of `.prev.json` for nothing; a different hash is two divergent copies claiming one number and is a `409`. Key order is sorted out of the comparison on purpose — the same state serialized by two code paths can come out ordered differently, and a retry that read as a divergence would raise the conflict bar over nothing.
- **A shrinking write is guarded, not refused.** Deleting is allowed; that is what the buttons are for. What is not allowed is the version before the deletion being gone five seconds later, which is all the single `.prev.json` could offer. The server stows the current file in `backups/guard/` before any write that loses `history` rows, empties a list that had rows, or drops more than two habits/goals/books/tasks/quotes/reads/badHabits. Guard filenames carry milliseconds and are never reused — two guards can land in the same second, and the first is the one that still had the rows.
- **The snapshots are reachable from inside the app.** Knowing a copy of Tuesday afternoon is on disk is no use to someone who would have to be told the path and paste JSON into an import box, so `GET /snapshots` lists all five kinds (`auto`, `daily`, `guard`, `manual`, and the verified copies in `backups/` itself) with enough of a summary to tell two apart — time, size, `rev`, `date`, that day's score, and a row count per section — and `GET /snapshots/<kind>/<name>` hands one back. **No path joining of anything a request said**: a name has to pass a strict regex *and* appear in the `readdir` listing taken a moment earlier, so the listing is the whitelist, exactly as `GRAPHIFY_FILES` is. Absent comes back as `null`, never `0` — `Number(null)` is `0`, and a snapshot with no revision reading as revision zero is a lie the compare screen would repeat. A restore writes the migrated payload to `localStorage` and **reloads**, so `loadState` does the migration and the day roll once and in one place; nothing is put into React state first, because a re-render there fires the save effect on the copy being replaced and puts it straight back.
- **A restore is guarded whether or not it shrinks anything.** `X-Guard: 1` stows the current file in `backups/guard/` before the write, unconditionally. `shrinkReason` cannot catch a restore on its own — the snapshot may well have *more* rows — and the one copy a restore must never destroy is the one he would undo back to. That is what makes «استرجع» reversible: the replaced copy appears in the recovery centre a second later, and undoing a restore is restoring it.
- **A second window reloads; it never gets promoted.** `useWriteLease()` stops two windows writing at once, but a *follower* that is handed the lease — because the other window closed — is holding a snapshot from before that window did an hour of work, and the save effect fires on the very next render. So a window that has ever been a follower does not become the leader: it calls `location.reload()` and comes back on the payload the other window actually left. Nothing is written first, not the lease and not the state. The lease is also re-read on `focus` and `visibilitychange`, because Chrome throttles a hidden window's timers to once a minute and `LEASE_STALE` is six seconds.
- **The last change before the window closes must reach the disk.** `syncOut` debounces at `SYNC_DEBOUNCE` (800ms) and `flushSync()` sends the pending payload immediately on `pagehide` and on `visibilitychange` to hidden, with `keepalive` when the body fits under the fetch standard's 64KB cap. Without it a tick followed by closing the window left the disk a change behind the browser — and the disk is what the reminders read and what a cleared profile recovers from.
- **The state itself lives in `life-state.mjs` and its eleven domain files, and they are the only thing under test.** The day boundary, the seeds, the shapes, `migrate`, `freshState`, `carryOf`, `rollDay` and `scoredOf`/`disciplineOf` are all there — everything the saved payload is made of and nothing that draws. The split exists so `node --test tests/` can load it without a browser, without React and without installing anything; esbuild folds it back in, so what ships is still one file. Two rules keep it loadable: **nothing in it touches `window`, `document`, `localStorage` or a lucide icon**, and **everything the app uses is exported** — a helper left behind is a `ReferenceError` at first render, which is a blank white page. The icon-carrying tables (`PILLARS`, `HORIZONS`, `COST_TYPES`, `URGE_TAGS`, `EVENT_KINDS`, `UNI_TASK_KINDS`) keep their ids, labels and tints there and have their icons fastened on in `LifeOS.jsx` by `fastenIcons`, **onto the same row objects, never onto copies** — the lookups that read those tables live on both sides of the split and the screens read `.icon` off whatever they hand back. `NAV_IDS` is the canonical tab list; `NAV` in `LifeOS.jsx` is built from it through `NAV_META`.

- **The source is thirty-three files, and every seam between them is checked by a test.** `LifeOS.jsx` is the entry point and holds the shell alone — the screens each live in a `life-*.jsx` of their own; `life-shared.jsx` holds the primitives every screen uses, `life-day.jsx` holds the pieces two screens render, `life-uni.jsx` holds the university desk, `life-finance.jsx` the income screen, `life-desks.jsx` the focus desk, `life-tools.jsx` the data tools, `life-styles.jsx` the ground, `life-storage.mjs` the save path, and `life-state.mjs` the state. esbuild folds them all back into one page, so what ships is unchanged. `life-state.mjs` is itself a thin core plus a barrel now: `life-state-util.mjs` holds the dependency-free day/date helpers every domain file is built on, and `life-state-habits.mjs`, `life-state-tasks.mjs`, `life-state-goals.mjs`, `life-state-books.mjs`, `life-state-calendar.mjs`, `life-state-uni.mjs`, `life-state-finance.mjs`, `life-state-bot.mjs`, `life-state-focus.mjs` and `life-state-streak.mjs` each hold one domain's constants, seeds and shape functions — the routine, the matrix, the goals vault, the shelf, the calendar, the university desk's state, the money, the bot's schedule, the focus desk, and the archive. `life-state.mjs` re-exports every one of them, so every other file still writes one `import … from "./life-state.mjs"` exactly as before; editing a list — the habit seed, the goal tree, the book shelf — means opening that one domain file, not hunting it inside 2,400 lines. **An import left behind is not the blank white page it sounds like.** `api`, `UI_KEY`, `OPENED_KEY` and `HANDOVER_KEY` were all missing from the import after `life-storage.mjs` was carved out, and every single reference to them sits inside the `try/catch` that storage code is *required* to have — so nothing threw where anyone could see it. The app rendered perfectly while `pullDisk` died on `api` before it could read the disk (a fresh profile booted on seed data at revision 0, and every save after it was refused as a conflict the user had no way to resolve), `readUI` always came back `{}` (a reload never returned to the screen he left), and the recovery centre listed nothing. **esbuild cannot catch this** — an undefined identifier is a bare global reference, not an unresolved import, and the build is clean. `tests/split.test.mjs` catches it instead, by text: for every name a module exports, if a file uses it and neither imports nor declares it, the build stops and names the module that owns it. **Exports were only half of it.** That check can only see what a module *exports*, and the hole in it is exactly the size of a helper carved into another file and left unexported — `horizonClock`, `clockLabel` and `HorizonRow` all moved to `life-goals.jsx` while `life-routine.jsx` went on calling them, and nothing caught it but a blank screen. So a second check holds every name declared at the top level of any of our files against every other file that uses it without importing or declaring it; that one found `LOCAL_HOST`, which `LifeOS.jsx` had been reading off `life-storage.mjs` unexported since the storage carve — inside a `try/catch`, so the stray-copy bar's «go to the primary copy» button had simply been dead. **And a template literal is not a string**: `strip` used to blank them whole, so a name used only inside `${…}` was never counted as used at all. `meetWord` escaped the check completely that way. The literal text still goes; the interpolations stay. A new split file goes in that test's `MODULES`/`CONSUMERS` lists and in the build's two arrays — **four registrations, and two of them used to be silent**. Missing from `scanned` or `shipped` fails a test; missing from `MODULES` or `CONSUMERS` failed nothing at all, because the lists that drive every check are the same lists the omission is in. They are held against the imports now, walked transitively from `LifeOS.jsx` rather than read off `CONSUMERS`, since a list cannot be the evidence for its own completeness. That guard found `life-storage.mjs` — it imports `uid` off `life-state.mjs` and had never been a CONSUMER, so the module whose four missing names caused the incident above had its own imports unchecked the whole time.

- **A pure helper two screens need belongs in the state layer; a pure helper one screen needs stays with that screen.** This is the rule that decides where a function lives, and it is the same cut rule stated from the other side: the moment the second screen needs it, leaving it in the first makes the first a dependency of the second over a function that has nothing to do with it. So the archive's own arithmetic moved down — `historyIndex`/`keptOn`/`habitStreak`/`levelOf` and `inReflectWindow` into `life-state-streak.mjs`, the mirror's counting (`weakSpots`, `dangerWatch`, `topShare`, `breakerEvents`, `breakerToday`, `cleanDays`, `bleedSaved`, `bestRun`, `HOUR_BANDS`) into `life-state-habits.mjs`, the shelf's (`bookForHabit`, `sumPages`, `readStreak`, `pctOf`) into `life-state-books.mjs`, the windows (`goalPct`, `goalEnd`, `windowOf`, `windowStand`, `openingWindow`) into `life-state-goals.mjs`, and the calendar's (`occurrences`, `eventsIn`, `upcoming`, `upcomingRows`, `alertsOf`) into `life-state-calendar.mjs`. Each one became testable on the way. `life-state-focus.mjs` reads `bandAt` off `life-state-habits.mjs` for the same reason `life-state-streak.mjs` reads `disciplineOf` there: the alternative was a second table of the day's hour bands, and the breaker's mirror and the focus desk disagreeing about when the evening starts. **The test is purity, not usefulness**: `horizonClock` and `nextPrayer` look like state and are not — the first returns `T.danger` in its `pace`, the second spreads a `PRAYERS` row with its lucide icon into the result — so both stayed in the view layer, and `nextPrayer` in particular must never move to `prayer-times.mjs`, which the sync server imports and which therefore cannot see an icon.

- **Two helpers doing one job is a bug waiting for the day they disagree.** `minsOf` (in `life-shared.jsx`) and `minsIn` (in `life-state-util.mjs`) parsed the same `"HH:MM"` the same way for three splits; only `minsIn` had a test, so `minsOf` is gone and its six call sites read the tested one. `resizeImage` was a second `shrinkImage` for book covers, and the weaker of the two: no `reader.onerror`, so a file the browser could not decode left the promise pending for ever and the upload button simply did nothing, and no budget walk, so an oversized cover went straight at the quota the whole year shares. One function now, with `COVER_STEPS` for the portrait case — `shrinkImage(file, COVER_STEPS)`. A step table is data; a second copy of the canvas dance is not.
- **`node scripts/build-life-os.mjs` runs the tests first and stops if they fail.** There is no CI and no second pair of eyes; that script is the only thing between a change and the page he opens. `--no-test` exists for debugging the build itself and means nothing is checking the state. New state behaviour gets a test in `tests/`, and the fixtures in `tests/fixtures/` are real backups — a migration that passes on an object invented to make it pass has tested nothing. The test that earns its keep most: **every key in `freshState()` must appear in `carryOf()`** unless it is on the short day-only list, because a key missing from the carry is data that exists all day and is gone by 04:00 with nothing on screen to say why.
- **The five prayers' names live with the maths, and the icons are fastened on.** `PRAYER_ROWS` and `clockAt` are in `prayer-times.mjs`: ids, Arabic labels, tints and the formatter, with no icon anywhere near them, because that file is imported by the sync server and one lucide import would take every reminder down with it. `PRAYERS` in `life-shared.jsx` is those same row objects with `.icon` assigned onto them — never copies, since `nextPrayer` spreads a row and every card reads `.icon` off what the lookups hand back. They moved down when a third reader appeared: the bot's morning brief lists the day's prayer times, and a second table of Arabic prayer names would be a second answer to a question with one.
- **The prayer maths lives in `prayer-times.mjs`, imported by both.** The app anchors its six blocks to those times and the server fires the reminders at them; a reminder landing on a different minute from the one on screen is worse than no reminder, because then neither number is trusted. esbuild pulls it into the bundle, so the built page is still one self-contained file — the split is in the source, not in what ships. Anything the app still needs from it (`fixHour`, and `prayerTimes` itself) must be **exported**: a helper left behind is a `ReferenceError` at first render, and a blank white page.
- **The reminders are Windows toasts, fired by the server.** A service worker cannot wake itself on a timer, so a browser-side reminder needs the window left open — which is the assumption being removed. `armToday()` schedules one timer per block and re-arms a minute past `DAY_START_HOUR`; the text is built from the state on disk, so it names what is actually still open instead of saying "don't forget". Windows shows a toast only for an identity it knows and **fails silently for one it does not**, so `TOAST_AUMID` is the installed PWA's app id — uninstall the app and the reminders quietly stop. The text goes to PowerShell base64-encoded: a habit's label is user-written Arabic that can hold a quote, and splicing it into a script turns a reminder into arbitrary code.
- Wrap every read and write in `try/catch` — the app must render correctly when storage is blocked.
- Never silently delete text the user typed. On a new day, uncheck; do not clear.

## Language

- **Arabic, strictly RTL.** `dir="rtl"` on the root, and the layout must read right-to-left natively — not a mirrored LTR design.
- **Never use English placeholders or labels in the UI.** Every `placeholder`, `aria-label`, `title`, button, heading and helper line is Arabic.
- Proper nouns are the only exception: the product name `2027 Life OS`, and exam or brand names such as `STEP`.
- Watch Arabic bidi: a Latin fragment or a spaced fraction (`5.7 / 10`) inside Arabic text reverses. Wrap it in `<span dir="ltr">`.
- Fonts: **Tajawal** or **Cairo**, with a real system fallback stack.

## Project layout

**The source lives under `src/`**, grouped the way a React project usually is — `features/` for the screens, `components/` for the primitives two or more of them share, `layouts/` for the navigation and the ground, `state/` for the payload, `utils/` for the save path and the prayer maths. The filenames keep their `life-` prefix on purpose: the folder supplies the grouping, and renaming on top of it would make every filename named in this document stale on the same day. `src/` is also what separates the app from the other things in this directory — the STEP arena, the vocabulary banks, the report agent — which is half of why the tree was hard to read.

**And the root holds nothing but doors.** `package.json`, `README.md`, `CLAUDE.md`, `.gitignore`, `.vscode/`, `.claude/` and the two shortcuts; everything else moved into the folder that says what it is — `scripts/` for what builds, `services/` for what runs in the background, `apps/` for the other pages, `docs/` for prose, `archive/` for what was superseded. Thirty-odd loose files at the root was not only untidy: it was a directory in which a live service and a patch script that ran once in October looked exactly alike, and the patch scripts were the ones holding absolute paths.

## Build

```bash
node scripts/build-life-os.mjs
```

It runs `node --test tests/*.test.mjs` first and stops if anything fails, then bundles `src/LifeOS.jsx` with esbuild, generates the exact Tailwind CSS by **scanning every `.jsx` source, not just the entry point**, and inlines both into `life-os/index.html` — then copies every local module into `life-os/` beside `LifeOS.source.jsx`, so the build and the source it claims to be cannot drift. Run it after **every** change to anything under `src/`; editing `index.html` by hand is editing a build artefact.

**esbuild follows the imports; the other two steps follow nothing.** The Tailwind scan and the published source copy are handed exactly the files `scanned` and `shipped` name in `scripts/build-life-os.mjs`, so a new split file has to be added to both by hand — and a test holds both arrays against what the source actually imports, because neither failure mode announces itself. Missing from `scanned`, a class used only in that file is dropped from the CSS and the screen renders unstyled with nothing in any log; that is how the university desk shipped, thirty classes short. Missing from `shipped`, the published source is one that cannot be built; that is how `life-storage.mjs` shipped, leaving a copy with no save path at all.

There is no `node_modules` beside `src/`. esbuild and tailwindcss are imported straight out of `life-os/node_modules` — a small `package.json` holding only those three packages, not an app of its own — and `lucide-react` resolves there too through esbuild's `nodePaths`. (This borrowed from `iron-log/node_modules` until Iron Log was deleted entirely, 2026-10-26; moved here rather than installed beside `src/`, so `src/` still has no `node_modules` of its own.) React is **not** bundled: it loads as UMD 18.3.1 from cdnjs and the bundle reaches it through shims that read `window.React`. `life-os/node_modules` holds no React at all — bundling one in beside a page loading 18.3.1 would give the app two Reacts and one of them would own the hooks.

Three things that have bitten this build before:

- **Never use `String.replace` with the bundle as the replacement string** — `$&`, `$'` and friends are substitution patterns and will corrupt the output. The build joins an array instead.
- **The project path contains a space** (`E:\claude code`). Any `file:///` URL must percent-encode it as `%20`, or Chrome opens nothing at all with no error.
- **The sync log prints characters, the disk holds bytes.** Arabic is two bytes a letter in UTF-8, so a payload logged at 24,627 is 28,839 on disk. It is not shrinking.

## Workflow

**One command per job, and `package.json` is where they are written down.** `npm run build` builds, `npm test` runs the state tests, `npm run dev` builds and then opens the app, `npm run serve:test` is the throwaway server below, `npm run report` redraws the charts. `.vscode/tasks.json` calls those same scripts rather than repeating their command lines, so the button in the editor and the line in the terminal cannot drift apart — Ctrl+Shift+B is the build.

**The editor's exclusions are load-bearing, not cosmetic.** `node_modules` anywhere in this tree (`life-os/node_modules` now holds the build's three borrowed packages; `services/telegram-bot/node_modules` holds the bot's own dependency) is excluded by a bare `**/node_modules` pattern. Add `graphify-out/cache`, `backups/`, and whatever full repo copies are parked in `.claude/worktrees`, and an editor watching the root watches a quarter of a million file handles — which is what makes the machine feel like the background services are hanging it. They are not: the sync server spends about a second of CPU a day. `.vscode/settings.json` keeps all of it out of the file watcher and out of search; do not trim that list to make a search find something, add the folder you actually want instead.

The app is served, not opened as a file. A `file://` page has no origin of its own: Chrome files every local html document on the machine into one shared storage bucket, will not install it, and will not mark its data persistent — so an ordinary "clear browsing data" takes the year with it. Served from `127.0.0.1` it has its own origin, and that is what buys persistence, installability and a service worker.

After building, restart the server if `services/local-sync-server.js` changed, then open it in the user's own Chrome so he can verify it himself:

```powershell
Start-Process 'C:\Windows\System32\wscript.exe' -ArgumentList '"E:\claude code\services\launchers\run-life-os.vbs"'
```

Confirm the window actually appeared before reporting success. **Any instance you open writes its whole snapshot to disk seconds after it mounts.** That is not a risk, it is the normal path — a headless check that set five core habits to photograph the result put those five, and a recomputed 60% on the day's archive row, straight onto the live copy. **Never open a second copy on the live origin while his is open** — the preview pane, a headless check, anything. Each one loads the state and writes its snapshot straight back on mount, so a window opened for twenty seconds of verification can land on top of a habit he ticked in that time.

**Verify on a throwaway copy instead.** The server takes `--port` and `--data-dir` precisely for this, and a server on any port but 47615 tells the page it serves that it is the primary copy for that server — so the write path, the conflict bar and the window lease can all be exercised in full without the live origin being involved:

```bash
node services/local-sync-server.js --port 47699 --data-dir life-os-test-data
```

Seed `life-os-test-data/lifeos.json` with a copy of the real one if realistic data is wanted; `life-os-test-data/` is gitignored and is deleted afterwards. Snapshot `graphify-out/data/lifeos.json` before any verification run regardless and diff it after — an `md5sum` either side is enough, and it should be byte-identical.
